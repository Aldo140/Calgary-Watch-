# Organization workspaces

The organization workspace is the management centre at `/organization/{business-id}` for an existing public business, or `/organization/org-{listing-id}` for a standalone organizer. A standalone workspace does not create a public business directory entry. Members & plans displays the approved company, source approval, role, linked upcoming event count and the same read-only workspace the member sees. Business dashboards link directly to it.

An approved business-profile claim authorizes the organization and its explicitly related events. A historical event/market approval gets a workspace for that listing and events added there; existing unrelated listings remain excluded until an admin explicitly confirms broader organization access in Claims. This is a deliberate authority grant, not an inferred entitlement from a shared venue. Approval repairs preserve the original decision date and email history.

A workspace draft bundles up to 100 additions, edits or removals across the profile, linked markets and events. Market date changes use the same submission and preserve date ownership. It is retained on the member’s current device. Review lists every change. A required confirmation explains that the complete submission uses seven days of allowance for the business, shared across all representatives. Members can draft their next changes while waiting. Images, provenance, ownership and identity remain protected. Removing an event hides its public listing and retains its images and audit record; it can be restored.

`submitOrganizationBatch` is an authenticated callable in northamerica-northeast1. One transaction rechecks actual approved claims, the trusted catalogue, pending legacy requests, target ownership and the shared weekly allowance; then writes all live projections, the allowance and a before/after admin notification. No member can directly write the catalogue, projections or allowance. Failed transactions publish nothing. A stable request UUID and payload hash make retries idempotent, including after a reload. No email is sent by this callable.

The public site shares one bounded listener for projections newer than its built snapshot, stops it while hidden and merges server content across discovery, search and dashboards. New event routes work before the next static build. Future exports merge projections and removal tombstones after feeds so an ingest cannot resurrect removed events. A subsequent Hosting release supplies static HTML, sitemap and crawler metadata; instant publication is visible to the JavaScript application immediately after the transaction, while static crawlers wait for that release.

## Activation

1. Deploy the latest Hosting build. Its post-deployment catalogue sync reads inventory once and writes changed canonical records only. A catalogue is necessary for safe server-side ownership checks.
2. Deploy rules and the new callable using the existing **Deploy Firebase Backend** workflow, target `all` (or rules and functions separately). Cloud Functions requires the project's supported billing and IAM configuration. Hosting alone does not activate the callable. The functions predeploy packages the shared TypeScript validation using the installed root dependencies.
3. Confirm historical event/market-only representatives’ organization authority in Claims. Do not invent approvals or broaden access automatically.
4. Verify with two representatives: one bundled add/edit/remove commits immediately, both see the same next eligible time, a second submission is rejected, another organization is denied, images cannot be changed, and admin preview cannot submit until an authorized admin explicitly enables editing.
5. Run the production roster audit documented in organization-coverage-review.md and review official programme pages for missing confirmed dates.

The existing scheduled publisher remains compatible with older queued and listing-only edits. New organization submissions are marked already published, so the legacy worker does not dispatch unnecessary releases for them. Both paths use the canonical business allowance. Historical audit records and sent-email records remain intact.

## Workspace presentation and read efficiency

Profile, Events & markets, and Weekly draft have separate navigation. The programme supports search and upcoming/past/cancelled/removed/market filters. Publishing stays available in a sticky review bar; image and publishing guidance is expandable. The member dashboard prioritizes the organization workspace and keeps source listing approvals in an expandable history. Admin member rows show managed organizations before opening details.

Canonical profile, programme and allowance data are loaded once per workspace mount, with an explicit retry for loading failures. Shared live projections update the workspace without repeating those reads on unrelated organization changes. Version-aware merging prevents a slow initial snapshot from overwriting newer removals or edits. Draft edits remain intact when switching sections or retrying a read.

Further client optimizations: draft persistence is debounced for 300ms and flushed on page hide, backgrounding and unmount; programme filtering is deferred and memoized, with 24-row progressive rendering; unchanged projection revisions retain their collection identity; date formatting reuses one formatter. Publishing functions load on submission. Phone, website, ticket and price inputs use appropriate mobile controls. The visible clock refreshes event states each minute and unlocks the weekly allowance at its deadline without a page reload. Browser checks with mocked Firebase confirmed 24/48-row pagination, search resetting pagination, and one draft write for a twelve-character typing sequence, alongside reload recovery and read-only preview.

## Admin access modes

Member dashboards, organization workspaces, listing management and Market HQ open read-only for admins. The “Enable admin editing” switch grants editing for the current page and subject; reloading or changing the account resets it. All verified administrators, including protected role-assigned admins, can use it. Member preferences and RSVPs save through an authenticated callable without impersonating the member or changing their identity or role.

Organization admin changes publish immediately, including approved primary/gallery image URLs, captions and credits. Admins can add and remove events through the organization workspace. File uploads are not provided. Admin saves bypass but do not consume the business’s seven-day allowance. Business owners retain their existing weekly limit and cannot change images. Admin edits are attributed to the actual administrator in audit records; conflicting older queued edits are superseded to prevent stale publication. Editing an unclaimed listing does not verify an owner.

Deployment requires updated Firestore rules and both `submitOrganizationBatch` and `adminMemberAction` functions, built by the existing functions asset packaging step. Authenticated production verification is still required. Local browser checks use mocked Firebase boundaries and cover default read-only access, explicit enable/disable, the selected-member admin payload and reset after reload. Server handler tests cover authorization, audit attribution, image preservation, weekly limits and idempotent RSVP counts.

Admin-mode validation: all 1,174 tests passed, TypeScript passed, functions bundles passed syntax checks, and the production build passed. Browser checks passed with mocked Firebase boundaries. Production deployment and authenticated live checks remain unverified.

## Organization-first claims and one-off organizers

The public CTA says “Own this listing?” and names the organization profile being claimed. An explicitly linked event or market points to the existing public business claim, with the originating listing kept as context. The claim page previews the prefilled profile before asking the representative’s identity and authority. Multiple representatives can request access to an already-claimed organization; this does not replace existing managers or skip approval. Claimed listings retain their verified presentation and expose “Manage or request access” instead of an ownership pitch.

When there is no public organization profile, the source listing itself remains the claim target. A deterministic management-only profile (`org-{sourceListingId}`) is prefilled from the source organizer and official link. The venue address is never invented as a company address. Organizer details persist in `organization_management_profiles/{sourceListingId}` only after a successful save and are readable by admins and approved representatives of that listing. They never enter public discovery, sitemap or business pages. The first view is Your listings, including the original market/event; the organizer can maintain that listing and add events in the same weekly batch. One listing is sufficient; a permanent public company page is an editorial decision, not a prerequisite for management.

The original public listing, dates, images, claim and email history stay in place. Shared limits use the canonical organization ID where available, otherwise the original source listing ID, so changing management URLs does not create another allowance. Past/removed sources can be recovered from the trusted catalogue and saved management profile. An old event-only approval does not acquire control of its company’s other events by name, venue, or domain matching. Server-created events retain their explicit workspace association if a later feed tries to reassociate them.

Market HQ accepts an approved exact market claim or approved access to its canonical linked organization. Explicit organization grants from historical listing claims use a protected `organization_managers` index with a live reference to the approval; revoking that claim removes access even if the index remains. New approval/repair writes this index atomically. Existing exact business-profile approvals work without it.

### Production activation for this change

Deploy the updated `submitOrganizationBatch` and `approveOrganizationClaim` functions and Firestore rules before Hosting, and synchronize the trusted organization catalogue using the existing release workflow. With production credentials, run `npx tsx scripts/claims/sync-organization-access.ts` once to index existing explicit organization approvals. This migration preserves existing approvals, dates, verification, account and email history; it grants no inferred organization access. The local environment has no usable production credentials, so deployment, indexing and authenticated production verification remain outstanding.

Only Firebase/auth boundaries were mocked. The emulator test includes Market HQ scope, revocation and forged memberships; it still requires the Firestore emulator artifact unavailable in this environment.


Approval/repair now uses `approveOrganizationClaim` to commit the claim, verified mark, Business account, organization membership, event migration and preserved weekly limit together. Expanding a one-off workspace requires an admin confirmation that the shared workspace’s already-approved representatives will all receive organization access; the server rechecks those representatives and migrates their grants atomically. Pending claimants are excluded, conflicting grants abort, and prior approval/email history is retained. Events never disappear into an inaccessible old workspace. Existing simple approvals retain the original atomic browser fallback if the new function is not yet deployed; organization expansion fails explicitly until the backend is deployed.

Programme CSV imports add up to 100 confirmed events into a local reviewable draft, using the same seven-day allowance. Required columns are title/start/end/address. Optional venue, summary, description, pricing and HTTPS tickets are supported. Organizer identity, images and ownership cannot be supplied in CSV. Duplicate title/start rows and existing organization events are rejected before any draft is changed. An audit-receipt size check aborts overly large server submissions atomically before consuming the allowance. Backend deployment is required for the expanded limit.
