# My Watch Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Turn Calgary Watch's ephemeral session notifications into a persistent, personalized "what changed near me since I last looked" loop, with a shared ranking engine, resident corroboration, and privacy-safe activation analytics.

**Architecture:** A pure `buildWatchFeed()` engine (no Firestore, no DOM) ranks the already-loaded incident set against the reader's home, last-seen time, and preferences, reusing the digest's existing `distanceMetres`/`digestHighlightScore`. The map's notification panel and the weekly email both consume it. Watch state persists on the Firestore `users` profile for signed-in readers with a localStorage fallback for signed-out. Resident feedback lives in a separate `incident_feedback` collection (one deterministic doc per user+incident) and analytics in a create-only `product_events` collection.

**Tech Stack:** TypeScript, React, Firebase (Firestore + Auth), Vite, `node:test` + `tsx` for tests, date-fns.

**Spec:** `docs/superpowers/specs/2026-08-29-my-watch-design.md`

## Global Constraints

- Tests run with `node --import tsx --test tests/*.test.ts` (`npm test`); typecheck with `npm run lint` (`tsc --noEmit`). Both must be green before every commit.
- Pure logic lives in `src/lib/*`; it must not import React or Firestore. UI wiring imports the pure lib.
- Analytics records **no** address, report text, or exact coordinates — neighbourhood name and a rounded distance bucket only.
- Feedback is signed-in only; one record per `{uid}_{incidentId}`, enforced in `firestore.rules`. Clients may never delete feedback.
- New `users` profile fields are optional and back-compatible (absent = current behaviour). `weeklyDigestTopics: []` means "no filter".
- Follow existing file idiom: focused pure libs, heavy explanatory comments in the house style already present in `src/lib/digest.ts`.
- Reuse, do not fork: `distanceMetres`, `digestHighlightScore`, `selectDigestHighlights`, `isCommunityFacingIncident`, `isPubliclyVisible`.

```ts
// src/lib/watch.ts
import type { Incident, IncidentCategory } from '@/src/types';
import { isCommunityFacingIncident } from '@/src/types';
import { distanceMetres, digestHighlightScore, type Point, type ScoredIncident } from '@/src/lib/digest';

export type WatchSection = 'emergency' | 'community' | 'official' | 'routine';

export interface WatchPrefs {
  /** Metres from home; null means no radius filter. */
  radiusM: number | null;
  /** Empty means every category. */
  categories: IncidentCategory[];
}

export interface WatchItem {
  incident: Incident;
  distanceM: number | null;
  section: WatchSection;
}

export interface WatchFeed {
  items: WatchItem[];
  counts: Record<WatchSection, number>;
  sinceSummary: string;
}

/** Which pane an incident belongs to, strongest signal first. */
function sectionOf(incident: Incident): WatchSection {
  if (incident.category === 'emergency') return 'emergency';
  if (isCommunityFacingIncident(incident)) return 'community';
  if (incident.data_source === 'official' || incident.data_source === 'system'
      || incident.category === 'infrastructure') return 'official';
  return 'routine';
}

const SECTION_RANK: Record<WatchSection, number> = { emergency: 0, community: 1, official: 2, routine: 3 };

export function buildWatchFeed(input: {
  incidents: Incident[];
  home: Point | null;
  since: number | null;
  prefs: WatchPrefs;
  now: number;
}): WatchFeed {
  const { incidents, home, since, prefs, now } = input;

  const scored: WatchItem[] = incidents
    .filter((i) => since === null || i.timestamp > since)
    .filter((i) => prefs.categories.length === 0 || prefs.categories.includes(i.category))
    .map((i) => ({
      incident: i,
      distanceM: home ? distanceMetres(home, { lat: i.lat, lng: i.lng }) : null,
      section: sectionOf(i),
    }))
    .filter((it) => prefs.radiusM === null || it.distanceM === null || it.distanceM <= prefs.radiusM);

  scored.sort((a, b) =>
    SECTION_RANK[a.section] - SECTION_RANK[b.section]
    || digestHighlightScore({ incident: b.incident, distanceM: b.distanceM } as ScoredIncident, now)
       - digestHighlightScore({ incident: a.incident, distanceM: a.distanceM } as ScoredIncident, now)
    || b.incident.timestamp - a.incident.timestamp);

  const counts: Record<WatchSection, number> = { emergency: 0, community: 0, official: 0, routine: 0 };
  for (const it of scored) counts[it.section] += 1;

  return { items: scored, counts, sinceSummary: summarize(counts, Boolean(home)) };
}

/** "2 neighbour reports, 1 outage and 1 official update near home." */
export function summarize(counts: Record<WatchSection, number>, hasHome: boolean): string {
  const parts: string[] = [];
  if (counts.emergency) parts.push(`${counts.emergency} emergency ${counts.emergency === 1 ? 'warning' : 'warnings'}`);
  if (counts.community) parts.push(`${counts.community} neighbour ${counts.community === 1 ? 'report' : 'reports'}`);
  if (counts.official) parts.push(`${counts.official} official ${counts.official === 1 ? 'update' : 'updates'}`);
  if (counts.routine) parts.push(`${counts.routine} nearby ${counts.routine === 1 ? 'item' : 'items'}`);
  if (parts.length === 0) return '';
  const list = parts.length === 1 ? parts[0]
    : `${parts.slice(0, -1).join(', ')} and ${parts[parts.length - 1]}`;
  return `${list}${hasHome ? ' near home' : ''}`;
}
```

### Task 3: Digest topics — DEFERRED to W3 (preferences)

**Finding during execution (2026-08-29):** `weeklyDigestTopics` is not a set of
incident categories. It is a fixed array of four content-interest keys
(`weekly_crime_stats`, `neighbourhood_incidents`, `market_events`,
`community_updates`) written identically at `MapPage.tsx:1308` and `:2128`, with
**no selection UI and no consumer** anywhere in `src`, `scripts`, or `functions`.

Honoring these values as a filter would have no user-visible effect (they never
vary) and would mean building consumption logic ahead of the selection UI — a
YAGNI violation. The genuine work here is a *preferences* feature: a topic (or
category) selector plus a defined topic→content mapping. That is moved to **W3**,
where preferences (quiet hours, categories, zones) are built together.

No code change in W0 for this task.
